# Apporo platform：4.3 退件分析與第二輪回覆

更新：2026-11-02。維持獨立 Apporo platform，使用 WOOW TECH 帳號發行；不附公司用印文件。

## 結論與證據界線

最有證據支持的主因是 **送審 build 1.0 (5) 與既有 woowtech platform 的核心功能及操作體驗重疊**。不同公司、服務地區與維運合約解釋了商業關係，但尚未讓 Apple 看到產品層面的差異。Apple 未指名比對 App，也未提供二進位相似度或特定畫面，因此「主要比對 woowtech platform」是根據同帳號產品及程式架構作出的判斷，不是 Apple 已明說的事實。

10/16 原訊息列出 4.3(a)、4.3(b)、4.2.6；10/31 00:10 的回覆強調二進位相似、功能、設計及整體使用體驗，並要求不同的內容與功能。它沒有要求用印文件，也沒有確認 4.2.6 已解除。11/2 重新送審前，App Store Connect 顯示 build 5「已拒絕／問題未解決」；本次完成後已改為 build 6「等待審查」。

## 分項判斷

| 問題 | 可核對的證據 | 對應處理 |
|---|---|---|
| 4.3(a)：同一產品的多個 Bundle ID | 同一 Xcode target 透過品牌設定產出兩款 platform；兩邊商店說明均提供 Odoo 登入、組織網站、多帳號、打卡定位、附件、App 鎖 | 承認共用底層，提供實際不同的使用主流程及可操作證據；不以改色、改圖示或降低程式碼相似度作為改善 |
| 4.3(b)：與既有產品難以區分 | Apporo 文案定位建築設施客戶，但 build 5 主要仍是一般 Odoo 用戶端；入口與主畫面結構接近 | 讓 Apporo 設施服務在產品操作上可辨識，展示從場域、工作紀錄到服務請求的完整流程；請 Apple 說明是特定 App 還是整體類別的比較 |
| 4.2.6：範本或 App 產生服務 | APPORO UNION 是品牌／服務提供者，WOOW 是開發維運及發行合作商；現有 aiot 也採此安排 | 分開請 Apple 判斷此具名開發維運關係是否被認定為商業範本／產生服務，以及認定依據；不將既有 aiot 核准當成豁免 |
| 審查可操作性：本次實測新發現，並非 Apple 已列的退件項目 | 審查帳號可登入，但 demo111 的 `project` 模組是 `uninstalled`；新功能原先使用 Odoo 18 已移除的讀取路徑 | 修正 API、配置專案模組與示範專案、以審查帳號完成建立／讀回實測；未完成前不能聲稱 Apple 可驗證新功能 |
| 送審材料與實際版本不一致的風險 | 提到設施工作台的 build 6 從未上傳；Apple 目前仍只有 build 5 | 新版、畫面、說明與示範帳號必須同時可用；回覆中明確區分候選功能與已提交版本 |

[Apple 指引](https://developer.apple.com/app-store/review/guidelines/#spam)要求功能與體驗能區分；[4.2.6](https://developer.apple.com/app-store/review/guidelines/#minimum-functionality)針對商業範本／App 產生服務的提交方式。授權維運與品牌使用權有助解釋發行關係，但不自動排除這兩類問題。不能承諾「只要補授權就會過」。

## 為什麼上一封說明不足

1. 回覆描述不同公司與區域，但既有版本沒有能讓審查員直接驗證的設施工作台。
2. build 6 仍在本機，新增原生列表及建立表單尚未跑通審查環境。即使完成這些功能，Apple 仍可能認為差異不足；我們不能把新增一個入口當成已符合 4.3。
3. TestFlight 的既有資料只有少量內部使用且沒有提交回饋，不能編造「經用戶回饋完成差異化」的案例。
4. Apporo aiot 是硬體控制產品；其核准有助說明相同發行關係，無法直接證明另一款 Odoo 用戶端符合 4.3。
